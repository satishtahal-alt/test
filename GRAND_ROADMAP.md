# Draw5 — Grand roadmap (approved 2026-10-01)

The planning pass audited the project and proposed this order; it was approved with the working rules below.
The assessment itself (what exists, what needs restructuring) is summarised in `CHECKPOINT_P1.md` §Context and in
`DRAW5_IMPLEMENTATION_STATUS.md` §13. This file is the plan: order, boundaries and **done criteria** per pass.

## Working rules (from the approval)

1. Keep this order. Change it only when implementation reveals a real dependency problem — and say so.
2. One pass at a time: implement only that pass, run the automated tests plus targeted manual verification, document
   what changed and the architectural decisions, checkpoint (`docs/CHECKPOINT_<pass>.md` + ZIP in `dist/`), stop.
3. Foundations are generic infrastructure, not shaped by the first feature that uses them. No shortcut that would
   later force replacing the Project, the Runtime Kernel, Entity Definitions or Sequencing.
4. Extend what exists. Do not replace the renderer, style system, generator contract, spatial / plane model or the
   ability runner. Never build a parallel version of an existing system.
5. 2D / 2.5D assumptions are fixed early as data (`PROJECT_FORMAT.md` §8); no rendering / 3D project before P13.
6. Existing `.dsf` content and workflows keep working; every format change states its migration.
7. Later phases are not implemented early. A pass leaves clean extension points and stops at its boundary.
8. Layer improvements and editor clean-up (E1, E2) float: they run between passes unless they become a dependency.
9. (2026-10-05) **Demo breadth.** The demo suite grows broader, not only larger: a new or extended demo looks for a
   genre, camera, structure, cast or tool the suite does not have yet, and new heroes, enemies and tools go into the
   libraries as reusable content. It is cumulative, never forced into a pass, and never a side project: engine
   capability → reusable assets → varied demos → eventually polished games. See *Demo breadth* below.
10. (2026-10-10) **A demo level per major capability.** A major capability is planned, from its first pass plan,
    with a level made for it in which it is played - not only unit tests, probes and the levels that exist. Each
    plan says which pass makes the level, or why none is needed.
    - *Made for it.* An existing level is used where the capability belongs there by nature (the audio work in
      the levels that were silent); never as the default to save the authoring.
    - *Distinct.* Before it is made the suite is read (*Demo breadth*) and a concept, place, aim or interaction is
      chosen that Draw5 has not shown; not one more platformer strip where the capability deserves another game.
    - *Played.* The capability is met as a player or a maker meets it, with the systems working on each other;
      things put into a scene to prove that they exist are not a demo.
    - *Kept.* The level stays in the project as an example, with a short play script or a note of what it shows
      (`docs/<LEVEL>.md` or a section of the pass's document) and which definitions to open to change it.
    - *Extended.* A milestone of several passes extends its one level; another level only for a use that is
      different in kind.
    - *Beside the tests.* The automated tests and the regression run as before; the level's tour joins them.
    - *Proportionate.* Distinct, finished and telling; never so large that it delays the engine work. If a pass
      runs long the level is cut smaller, not dropped and not moved without saying so.
    First use: the Proving Ground, made in P15.2 and extended in P15.3 and P15.4 (`P15_PLAN.md` §11).

## Phase 1 — Foundations

### P1. Project container, scenes, Save / Save As — ✅ done
Done criteria and results: `PROJECT_FORMAT.md` §10, `CHECKPOINT_P1.md`.

### P2. Runtime kernel — ✅ done
Done criteria and results: `RUNTIME_KERNEL.md` §11–12, `CHECKPOINT_P2.md`. The plan as approved:
* **Purpose:** one model for how runtime systems exist and how entities come and go.
* **P2a — system registry + entity records (behaviour-preserving).** Existing subsystems (states, environment,
  engine, AdvFx, behaviours, rigs, collision, reactions, combat, creatures, binding, fills, fx) become registered
  systems with a lifecycle (`collect`, `start`, `step` in a declared phase, `stop`, `describe`). One runtime record
  per entity replaces the id-keyed side tables as the place per-entity state hangs. `project.systems` selects /
  configures systems per game.
* **P2b — spawn / despawn.** Real runtime creation and removal of entities (pooled), from any asset or definition;
  a `spawn` action and ability op; projectiles may be full entities.
* **Depends on:** nothing new (uses P1's `project.systems`). **Reuses:** every existing subsystem, the action
  contract, `renderer.mountRuntime`.
* **Done when:** (a) frame order and behaviour are unchanged — all level demos pass with identical step counts and
  the 250+ unit tests pass; (b) no subsystem is started by a hard-coded call or `if (this.xStart)` in `world.js`;
  (c) a game can switch a system off in `project.systems` and it neither starts nor costs frame time; (d) an entity
  spawned mid-Play collides, reacts, takes damage, is drawn in its plane and is removed again without leaks
  (memory / node count return to the baseline in a probe); (e) a flower asset can be fired as a projectile by data
  only; (f) a new system can be registered by a module through a contract, with validation.
* **Risk:** regressions in `world.js` / `runtime.js` — hence the split and the demo suite as the guard.
* **Enables:** P3, encounters, vehicles, destruction, summons.

### P3. Entity definitions, stats, variants — ✅ done
Results: `CHECKPOINT_P3.md`. Amended on 2026-10-01 (`P3_PLAN.md`): the pass also laid the **action layer** (motion state,
momentum as data, action history, sequences of actions, control contexts, feedback), built examples A–E by composition
only and the test level **Motion Lab**. The eight native movement actions stay code until P7. The plan as approved:
* **Purpose:** one definition / instance / variant model for characters, creatures, bosses, vehicles, projectiles,
  items and interactive objects.
* **Changes:** definition kind `entity` (components: look, movement, combat, abilities, AI, parts, stats…);
  instances `{def, overrides}` built like generator instances and spawnable at runtime; one `extends` + sparse
  override rule for **every** definition kind (resolved in `Definitions`); a stat modifier stack (base → parts →
  equipment → statuses → level); statuses as data. Creature definitions (D5CRT) become entity definitions; old
  files keep importing.
* **Depends on:** P1 (project scope), P2 (spawn). **Reuses:** generator instance contract, component slots,
  combat, ability parameters, creature runtime.
* **Done when:** (a) Petal Hollow (142 steps) and Crimson Moon (278) pass unchanged on migrated definitions;
  (b) "Use as projectile / weapon / shield / item" wraps any asset without copying it; (c) a variant overrides one
  field and inherits the rest, for at least entity, ability and AI kinds, through the same resolver; (d) a body
  part contributes stats that change movement (the "robotic legs" case) by data only; (e) an instance survives
  save → load and scene duplication; (f) no second prefab mechanism was added — saved assets, generator instances
  and creatures are explained by the one model in the docs.
* **Risk:** over-generalising; keep the component set to what existing games use.
* **Enables:** P5–P8, P15, P16.

### P4. Sequences, camera director, clock, editor viewport — ✅ done
Results: `CHECKPOINT_P4.md`; plan and what changed: `P4_PLAN.md`. One usability item was added by the user on
2026-10-02: instructional text shown for PC or for a gamepad (control hints). The plan as approved:
* **Purpose:** anything that happens over time on purpose: cutscenes, boss intros, camera moves, tests.
* **Changes:** the demo runner's step engine becomes the shared sequence runner (definition kind `sequence`);
  a clock model (gameplay clock pausable, presentation clock running; hit-stop becomes one use of it); camera
  shots, paths and blends as data; the editor camera is separate from the Play camera; Play from here; effects
  preview while editing.
* **Depends on:** P2. **Reuses:** `demo.js`, camera rig, shake, states, reactions. From P3: one entry point for requesting an
  action on an entity, `rec.control`, the per-entity `timeScale` stat. A sequence orders actions across entities and
  time; within one entity the ability runner already sequences (`use … then`).
* **Done when:** (a) all demo scripts run through the shared runner with identical results; (b) the boss-intro
  example works end to end by data (pause gameplay → pan → reveal → focus → return → resume); (c) Play can start
  at a chosen point without replaying; (d) the editor view is never changed by Play; (e) hit-stop and pause use the
  same clock API.
* **Risk:** demo determinism; touching hit-stop. **Enables:** P8, P9, P17.

### P13 scope: the dimensional companion (added 2026-10-03; its visual half is built in P13.0, light and shadow in P13.1, its height channel in P13.2)

Goal: the shapes, characters, environments and geometry already authored in Draw5 gain convincing, or limited actual,
dimensionality. Draw5 makes what is already authored feel dimensional; it does not become a general 3D engine and it
does not need a separate 3D modelling workflow.

Possible capabilities: extrusion of existing shapes · simple boxes / volumes · walls · ramps · prisms · cylinders ·
height-aware platforms and obstacles · stylized side-face shading · bevel-like treatment · dimensional treatment of
Draw5-authored characters · limited height-aware gameplay · simple top-down spatial relationships.

Approach the audit found compatible (`DIMENSIONAL_COMPANION_AUDIT.md`): derived geometry on Canvas2D / Konva, drawn
by the existing style system; optional height; derived presentation faces; limited height-aware collision.
A general WebGL / full-3D renderer is not the direction (it stays under *Not to be built yet*).

**Kept open until then (P7 – P12).** Nothing is built for these; a pass only avoids closing the door:

1. `scene.dimension.view` stays available as a future concept (`side`, `top-down`, `oblique`). The field is reserved (`PROJECT_FORMAT.md` §8).
2. Future height is an optional scalar per gameplay plane, not a general x / y / z world.
3. Derived dimensional faces are presentation only; they are not stored as document geometry of their own.
4. Collision leaves room for a height band, and no new gameplay rectangle is measured from drawn bounds.
5. The particle schema (P12) can take an optional height and vertical speed.

No speculative system is added for any of the five.
